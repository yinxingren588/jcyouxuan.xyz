日志有助于定位失败发生在哪一步，但它也可能暴露订阅令牌、账户信息和访问内容。有效排障并不要求把整个配置、全天日志或浏览器档案公开上传。先确定需要回答的问题，再收集最小范围材料。

## 从一个短时间窗开始

记下准备复现的时间，只执行一次目标操作，然后结束记录。保留错误前后必要的上下文，而不是只截一行末尾报错。重复操作过多会让日志混入重试、其他应用和自动更新，反而更难解释。

若要导出浏览器网络记录，先阅读[Chrome 网络面板参考](https://developer.chrome.com/docs/devtools/network/reference/)中有关导出的说明。工具可能提供经过处理的导出方式，但不能因此假定文件已不含敏感 URL 或请求正文；分享前仍需检查。

## 哪些字段优先脱敏

| 内容 | 建议处理 |
| --- | --- |
| 订阅链接、令牌、授权头 | 整段移除或替换为明确占位文字 |
| Cookie、会话标识 | 不发送原值 |
| 邮箱、订单、设备地址 | 只留定位必要的脱敏部分 |
| 错误码、版本、时间和阶段 | 尽量准确保留 |
| 私密页面正文、上传文件内容 | 不作为普通排障附件提供 |

脱敏应保留结构意义。例如可写“订阅域名已隐藏，返回 403”，不要把状态码也一并涂掉。若技术支持确需额外字段，先明确用途和提交渠道。

## 截图和文件都要复查

截图注意地址栏、侧边栏账户名、二维码与后台页面；纯文本则搜索 `token`、`Authorization`、`Cookie` 等可能字段，也人工检查 URL 查询参数。不同软件的字段名不一致，关键词搜索不能替代复查。

不要把原始附件上传到公开论坛再让别人替你判断敏感性。使用服务方确认的私人支持入口，并只发送解决当前问题必要的部分。临时生成的记录在问题结束后按自己的保留策略处理。

## 发现泄露时如何收尾

若完整订阅或登录凭据已经发出，删除公开内容后，还应按服务方流程撤销或更换相关令牌；仅删除截图不等于已撤销访问能力。保留事故时间与处理结果，但不要再复制泄露值。

日志本身不能证明品牌长期性能。它用于解释一次可复现故障，配合[工单清单](/blog/diagnose-support-ticket/)与[观察记录方法](/blog/stability-evidence/)才更容易形成可检验结论。

## 脱敏后检查信息是否仍然连贯

同一个对象在多处出现时，使用一致代号，例如“目标甲”和“配置甲”，不要每行都换一个名称。否则维护方无法看出请求、错误和重试是否属于同一事件。时间可以保留必要精度，但若确实需要隐藏活动规律，应说明时间已作统一偏移。

原件与脱敏件分开放置，提交前确认选中的是后者。压缩包还要检查文件清单，避免把备份配置、账户截图或临时导出的原日志一起打包。支持方收到后若仍无法定位，先补充明确需要的字段，不必把全部原始材料一次性发送出去。
