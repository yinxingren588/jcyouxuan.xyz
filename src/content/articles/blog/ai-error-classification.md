API 出错时，先保留完整的错误结构再处理。只截取一句“请求失败”，会丢失状态码、错误类型和请求编号，使账户问题、参数问题和连接问题混成同一种故障。

## 收到响应与没有响应分开记录

收到结构化错误，说明请求至少走到了能返回该错误的环节；本地连接超时则可能尚未获得目标服务响应。中间网关也可能返回自己的错误页，因此应确认响应来自哪个主机和系统，不把任何状态码都归给模型服务。

[OpenAI 官方错误文档](https://developers.openai.com/api/docs/guides/error-codes)提供 API 状态与处理建议。阅读时结合错误正文，不能仅凭一个数字决定重试，更不能把所有拒绝都解释成网络限制。

## 按原因选择修复动作

| 类型 | 有针对性的动作 |
| --- | --- |
| 认证或权限 | 核对项目、密钥来源和授权 |
| 请求参数 | 检查字段、格式和当前接口要求 |
| 额度或限速 | 查看具体错误与用量设置 |
| 临时服务异常 | 按官方建议有限等待和重试 |

例如模型名拼写错误，反复更换网络没有针对性；凭证权限不足也不能靠增大超时解决。若错误提示涉及所在地或服务资格，应遵守官方使用条件，不尝试伪造账户信息。

## 最小化请求以确认配置

在允许的测试环境中，去掉文件、工具和长历史，只保留当前接口所需的最小输入。若最小请求成功，再逐项恢复功能。每一步记录改变了哪一项，避免同时升级 SDK、替换密钥和改模型后无法比较。

不要把真实客户资料作为测试样本。公开求助时只提供脱敏字段和结构，用说明性的标记替代密钥、邮箱及私密内容。必要的请求编号可以通过正式支持渠道提供。

## 给结论设定证据边界

一次最小请求成功，只说明那次请求和权限配置可用，不能证明长任务或所有模型都通过。若问题间歇出现，保留成功与失败两组记录，对比时间、请求类型和并发量。

解决后应回到原任务验证，并撤销不再使用的临时设置。重试本身也可能产生额外请求或重复动作，遇到限速可读[有上限的重试策略](/blog/ai-rate-limit-retries/)，生成途中断开则参见[流式中断处理](/blog/ai-stream-interruption/)。
