DNS 查询很快，网页仍可能慢；重复查询更快，也可能只是缓存已经存在。比较解析体验，需要记录问了什么、通过谁问、缓存怎样处理，以及结果是否足以支撑后续连接。

## 固定问题比固定工具更先一步

同一域名的不同记录类型不是同一个问题，查询一个热门已缓存域名和一个首次出现的域名，也不是相同条件。开始前写明域名、记录类型、查询来源与实际使用的解析路径。

[Microsoft 的 Resolve-DnsName 文档](https://learn.microsoft.com/en-us/powershell/module/dnsclient/resolve-dnsname)列出指定服务器和记录类型等参数。使用命令时应理解参数用途，不把一组陌生开关当成万能网络修复。命令结果只覆盖该次系统查询，不会自动代表浏览器内置解析或客户端 DNS 模块。

## 把缓存状态写成可解释的条件

首次查询和紧接着的重复查询分别记录，不用后者代替前者。操作系统、应用、路由器和递归解析器都可能有自己的状态，普通用户通常无法同时控制全部层次，因此报告应写清自己实际控制了哪一层。

不必为了比较多次重置全系统。清理缓存会影响其他应用，组织内部域名还可能依赖特定解析配置。保持日常设置下的自然观察，也可以回答“实际使用是否反复失败”这类更贴近需求的问题。

## 查询结果不能只有耗时

| 记录项 | 作用 |
| --- | --- |
| 查询名与类型 | 确认比较同一问题 |
| 工具与解析来源 | 说明请求走哪条路径 |
| 缓存处理 | 区分首次和重复状态 |
| 回答或错误 | 避免只选成功样本 |
| 随后连接结果 | 检查解析之外的阶段 |

假设一组查询返回很快但域名拼写错误，显然不能称作可用性改善。若不同解析来源返回不同 CDN 地址，也不能只看地址不同就认定其中一方错误，需要结合目标服务设计和真实访问验证。

## 何时停止比较并转向排障

一旦出现明确解析错误、长时间无回应或组织内部域名异常，应按[DNS 故障排查](/blog/diagnose-dns-failure/)处理。继续堆积很多成功查询，不能解释那个失败任务为什么发生。

恢复后使用原域名、原应用和原任务验证，不仅确认命令获得答案。结论限定为当前路径与日期，不写成某个解析来源对所有站点永远更快。基础概念见[DNS 词条](/glossary/dns/)，网页各阶段的关系见[网络瀑布图](/blog/observe-network-waterfall/)。
