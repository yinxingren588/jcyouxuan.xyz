克隆结束后，图片或模型文件只有几行文本，不一定是下载被截断。仓库可能使用 Git LFS，当前得到的是指向实际对象的指针。先识别文件类型，再决定是否需要补取大文件。

## 指针是引用，不是原始素材

[GitHub 的 Git LFS 说明](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-git-large-file-storage)解释了仓库保存指针、实际大文件另行获取的机制。打开疑似文件时，如果看到 LFS 版本、对象标识和大小等字段，应按 LFS 流程检查，而不是把这些文本保存成图片格式。

普通 Git 拉取成功只证明相应仓库数据可取得，不证明 LFS 对象都已下载。源代码压缩包是否包含实际对象，也应看仓库设置和下载方式，不能一概而论。

## 先确认项目本来就使用 LFS

查看项目说明和受跟踪文件规则，确认目标路径属于大文件管理范围。再检查本机是否安装并启用项目要求的工具，下载是否被显式跳过。不要直接删除指针文件，否则会让后续排查缺少线索。

如果项目属于团队，先问维护者预期的初始化步骤。部分对象可能需要独立授权或受使用量条件影响，应根据实际错误处理，而不是从搜索结果随意换到未经批准的镜像。

## 将失败过程分成三段

| 阶段 | 要核对的信息 |
| --- | --- |
| 仓库读取 | 分支和普通文件是否正确 |
| 对象下载 | 哪个对象、哪一步及具体错误 |
| 本地使用 | 文件大小、格式与程序识别 |

例如多个素材中只有一个失败，记录其对象与路径比重拉整个仓库更有效。补取完成后应确认实际文件能够打开，不能只看下载命令退出成功。

## 完整性验证优先于重复下载

若维护者提供校验信息，可核对对象或发布文件；同时确认应用打开的是正确路径，没有使用缓存中的旧指针。下载特别大的素材前，应检查存储空间和计费流量，避免中途因本地磁盘不足失败。

最终记录应包括仓库版本、缺失对象、处理步骤和验证结果。不要把“网页能打开、LFS 失败”简单写成某品牌服务全面不可用。传输路径的基础区别见[Git HTTPS 与 SSH](/blog/work-github-https-ssh/)，大文件断点问题可读[恢复下载](/blog/work-download-resume/)。
