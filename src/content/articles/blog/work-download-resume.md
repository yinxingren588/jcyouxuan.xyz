大文件下载到一半中断，不必立即删除已经取得的部分，但也不能盲目把新数据接到旧文件后面。先确认远端对象没有变化、下载链接仍然有效，并了解当前工具是否支持该场景的续传。

## 保存部分文件和原始来源

记录官方下载入口、文件版本、目标名称与已下载大小。临时签名链接可能过期，恢复时应从正规入口重新取得，不向第三方网站提交带授权参数的地址。

如果下载目标会被发布方替换，必须确认本地部分与远端仍是同一对象。不同版本混接可能形成大小看似正确、内容却不可用的文件。重要资料应先保留部分文件的副本，再尝试恢复。

## 续传能力由两端共同决定

[curl 的官方手册](https://curl.se/docs/manpage.html)说明了 continue-at 等续传选项及限制。工具提供选项不代表每个服务器和每种传输都支持；网页文件下载、表单上传和应用专用同步不能直接使用同一恢复方法。

普通用户优先使用官方下载器或浏览器已有的恢复入口。若工具明确提示不支持，不要强制拼接或忽略错误；先查服务方说明，必要时重新下载到另一个文件名，避免覆盖唯一副本。

## 恢复前检查四个条件

| 条件 | 检查理由 |
| --- | --- |
| 同一文件版本 | 避免把不同对象拼接 |
| 链接和权限有效 | 过期响应可能不是文件内容 |
| 本地空间足够 | 防止写入中途再次失败 |
| 工具支持当前方式 | 下载与上传限制不同 |

如果收到 HTML 登录页而非目标文件，不应继续把它当压缩包解压。检查响应与实际格式，避免仅凭扩展名判断成功。

## 完成后校验可用性

有发布方提供的校验和或签名时，按其说明核对；没有时至少检查预期大小、文件格式和实际打开结果。压缩包能列目录不一定说明所有内部文件无误，重要材料应完成必要的内容验证。

下载成功以后再删除不需要的部分副本，保留来源和版本记录。续传可以减少重复传输，却不保证减少所有计费流量，具体取决于已传数据和服务规则。开发素材属于 Git LFS 时，可先看[大文件对象机制](/blog/work-git-lfs/)。
