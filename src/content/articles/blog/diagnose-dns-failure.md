网页打不开不一定是 DNS；已经显示服务器返回的错误页，往往说明请求走到了更后面的阶段。只有确认失败发生在名称解析，才值得调整解析设置，否则容易把证书、代理规则或站点维护问题掩盖掉。

## 什么证据支持先查解析

浏览器显示明确的域名解析错误，客户端日志出现解析失败，或者同一个域名在相同条件下持续无法获得回答，才是有用线索。直接输入网站 IP 不是通用验证办法，HTTPS 证书、虚拟主机和站点路由都可能依赖域名。

[Microsoft 的 DNS 客户端排查文档](https://learn.microsoft.com/en-us/troubleshoot/windows-client/networking/troubleshoot-dns-client-resolution-issues)列出了客户端配置、不可达 DNS 服务器、Hosts 条目和中间设备等不同原因。它支持分层检查，而不支持“全部换成某个公共 DNS 就能修好”的结论。

## 先确认究竟是谁在解析

查看系统网络设置中的 DNS 来源，再查看浏览器是否启用独立的安全 DNS，以及连接客户端是否有自己的 DNS 模块。三个地方并存时，系统查询正常并不能证明浏览器或代理内核也正常。

Windows 可在 PowerShell 使用 `Resolve-DnsName`，后接你实际要排查的域名。记录查询时间、答案类型与报错即可，不要把返回地址当作所有网络环境都应一致的标准答案。CDN 和不同解析视角可能返回不同结果。

## 按证据选择下一步

| 观察 | 优先调查 | 不宜直接下的结论 |
| --- | --- | --- |
| 系统查询失败，其他设备正常 | 本机配置、Hosts、过滤设置 | 全网 DNS 故障 |
| 系统查询成功，只有某应用失败 | 应用的独立解析路径 | 系统缓存一定损坏 |
| 多设备在同一 Wi-Fi 失败 | 路由器或上游接入 | 某个品牌节点全部失效 |

改动前把原来的自动或手动设置记下来。每次只调整一个解析来源，重新执行同一个查询；企业、学校设备的内部域名可能依赖组织 DNS，应由管理员确认后处理。

## 修复必须回到真实任务

获得解析答案只是第一关。继续验证网页连接、证书与实际功能；如果仍失败，沿着新出现的错误往后查。清理缓存只能影响缓存相关状态，不能修复不可达服务器或错误规则。

不要长期禁用系统 DNS 缓存，也不要把所有内部域名发送到陌生解析服务。详细概念见[DNS 词条](/glossary/dns/)，若只在一个浏览器异常，可以继续阅读[网页与应用表现不一致](/blog/diagnose-web-app-difference/)。

## 名称本身也需要核对

复制域名时检查拼写、末尾空格和是否误带了页面路径。站点可能已经更换入口，旧域名失效并不能靠清理缓存修好；应从自己确认的官方渠道核对入口，不从搜索广告随意替换订阅或登录地址。

对于只有组织内部才存在的名称，离开组织网络后无法解析可能属于预期设计。不要把它当成公共解析器能力不足，也不要把内部名称列表公开给陌生人。若维护方要求提供查询结果，保留问题名称的用途和记录类型，敏感部分可用一致代号替换，并说明已做脱敏。
