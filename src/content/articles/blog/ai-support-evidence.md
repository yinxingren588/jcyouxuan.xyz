“AI 又不能用了”很难让支持人员定位。有效工单需要说明目标、失败位置和可查询的请求信息，同时把私密输入与凭证排除出去。材料不必多，但应能对应到一次真实的失败。

## 先确认问题交给谁

如果使用第三方应用，先判断错误出自该应用、它的代理服务还是模型接口。页面打不开与 API 返回错误属于不同问题。向网络服务方报告时给连接现象；向应用方报告时给复现步骤；向平台支持提交时按其要求提供请求信息。

不要将所有支持方加入同一公开群聊并发送完整日志。不同接收者需要的数据不同，材料应按用途最小化。

## 请求编号用来关联一次请求

[OpenAI API 概览](https://developers.openai.com/api/reference/overview)说明了请求编号与相关响应头，建议保留请求标识以协助排查。它不是密钥，也不能代替具体错误和时间；没有取得编号时，应如实注明未收到响应，而不是编造一个。

记录时间时写清时区，并区分开始和失败时间。对自己开发的应用，可在内部日志用任务标识关联多个请求，避免一次用户操作对应多次重试后失去线索。

## 用一页材料描述问题

| 工单内容 | 示例写法 |
| --- | --- |
| 预期 | 一个简短输入应返回文本结果 |
| 实际 | 收到某错误类型或中途停止 |
| 环境 | 系统、应用或 SDK 版本 |
| 复现 | 最少操作与脱敏样例 |
| 关联 | 时间、时区和请求编号 |

标明是否每次发生，以及最后一次正常工作的条件。若已经做过对照，写清只改变了哪一项，不要把尝试过的十几个无关操作堆成结论。

## 发送前清理，收到答复后复验

移除 API 密钥、会话 Cookie、私人附件和完整账户资料。需要保留结构时使用一致的替代标记。若错误只在真实文件中出现，先提取可安全分享的最小样本，必要时按正式私密渠道处理。

收到建议后一次执行一项，回到原任务验证，并将结果补充到工单。若恢复只是暂时的，应记录复发时间。日志安全可参考[脱敏清单](/blog/privacy-log-redaction/)，错误原因分类则看[API 报错判断](/blog/ai-error-classification/)。
