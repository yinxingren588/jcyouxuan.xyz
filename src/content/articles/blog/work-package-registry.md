安装依赖出现失败，首先要知道失败的是哪一个包、正在访问哪个仓库。整个项目可能同时依赖公开包、私有包和安装阶段下载的资源；把全局仓库改成一个镜像，未必覆盖所有请求，还可能影响认证与来源。

## 先保留第一个有用错误

记录包名、版本、目标主机、错误类型和命令环境。安装日志末尾的“失败”可能只是汇总，真正原因在更早的位置。不要只复制最后几行，也不要将带有令牌或私人仓库地址的完整日志公开发布。

[npm config 文档](https://docs.npmjs.com/cli/v11/commands/npm-config/)介绍了配置读取与管理方式。先确认当前项目实际配置，再判断是否存在用户级或环境级设置影响，避免修改了没有生效的一层。

## 仓库配置和包作用域分开看

[npm 的 .npmrc 文档](https://docs.npmjs.com/cli/v11/configuring-npm/npmrc/)说明了配置文件及认证作用范围。私有作用域包可能指向专用仓库，其权限要求与公开包不同。认证信息应限制给正确的仓库，不能随意复制到所有地址。

如果公开小包可取、某个私有包失败，应优先检查权限和项目配置；如果包元数据可读取、安装脚本下载失败，再检查脚本访问的实际资源，而不是只测试 registry 首页。

## 以最小变化做比较

| 现象 | 检查方向 |
| --- | --- |
| 单个包找不到 | 名称、版本与仓库是否正确 |
| 明确认证拒绝 | 令牌、作用域和访问权限 |
| 请求超时 | 目标主机与当前连接 |
| 安装脚本失败 | 脚本依赖的额外下载 |

先使用项目的锁定文件与规定版本，避免把升级依赖和网络排查混在一起。确需临时改变仓库时，限定范围、保存原配置，并遵守团队的软件来源政策。

## 验证安装之外还要验证项目

安装成功后执行项目要求的必要检查，确认依赖内容与锁定版本一致。不要因为重试通过就删除锁定文件或跳过完整性检查。临时令牌和配置在排查结束后及时撤销或还原。

最终工单应指出失败包与失败环节，不能只写“开发网络不行”。代码仓库与包仓库也不是同一连接场景，可对照[Git 连接检查](/blog/work-github-https-ssh/)理解，日志分享前参考[脱敏方法](/blog/privacy-log-redaction/)。
